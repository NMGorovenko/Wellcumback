# Свой сервер FRIENDSLOP

Собственный VPS необязателен. Настольная игра умеет поднимать сервер в локальной сети и пробовать временный интернет-туннель. Этот пакет нужен для постоянного адреса или если туннель недоступен. Он передаёт состояния комнат; сама симуляция выполняется приложением ведущего, которое должно оставаться открытым.

## Варианты коопа без Cloudflare

Для совместной игры в РФ без Cloudflare рекомендуемый следующий вариант — прямой
WebSocket relay на VPS в России. На 13 сентября 2026 сервер ещё не выбран и не
арендован. Для игроков из Красноярска сначала сравнить задержки до Новосибирска
и Москвы у обоих провайдеров связи, затем выбирать площадку. Например,
[Timeweb Cloud указывает обе локации](https://timeweb.cloud/docs/nashi-data-centry).
Географическая близость не гарантирует лучший маршрут. Это рекомендация для
размещения существующего пакета, а не обещание измеренного пинга.

Без своего VPS можно использовать общую overlay-сеть. Tailscale предпочитает
прямой UDP-путь и использует relay, если он недоступен; для приёмки проверить
фактический тип соединения через `tailscale ping`/`tailscale status`.
[Документация](https://tailscale.com/docs/reference/connection-types).
Прямой сервер дома потребует доступного внешнего адреса и маршрута до порта;
CGNAT может этому мешать. Подключение обычного VPN для выхода в интернет не
создаёт автоматически доступ между двумя игровыми компьютерами.

В настольных клиентах хост выбирает IPv4 виртуального адаптера в режиме
«Одна сеть / VPN» и отправляет приглашение `WCB1:…`. Поддерживаются Tailscale
`100.64.0.0/10` и частные диапазоны `10/8`, `172.16/12`, `192.168/16`, которые
можно использовать в ZeroTier. Нужен доступ к выбранному TCP-порту между
участниками; игра не устанавливает VPN и не меняет его правила. В приглашении
используется числовой IPv4, а не имя MagicDNS.

Для этого варианта предпочтительны приложения Mac/Windows. Подключение HTTPS-сайта
к частному `ws://` ограничивается браузером; для сайта использовать сервер с WSS
и действительным сертификатом. Переносной HTML предназначен для локальной игры
и сетевые подключения запрещает. Реальная пара через Tailscale/ZeroTier ещё не
проверена. [Ограничения браузерного WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_client_applications#security_considerations).

## Локальный запуск пакета

Нужен Node.js 22.13 или новее. Пакет `server.zip` уже содержит зависимости: `npm install` не нужен. В исходниках тот же пакет собирается командой `npm run build:server`.

```sh
export WELLCUM_ACCESS_KEY="$(node -e 'process.stdout.write(require("node:crypto").randomBytes(32).toString("hex"))')"
node server.mjs
```

По умолчанию сервер слушает `127.0.0.1:8787`, комнаты хранятся в памяти. `HOST=0.0.0.0` открывает доступ из локальной сети. `WELLCUM_DATABASE` задаёт файл SQLite; папка должна существовать и быть доступна пользователю процесса. Остановка — Ctrl+C. `/health` показывает работоспособность и версию протокола без ключей или данных участников.

## Постоянный адрес на Linux

1. Распаковать пакет в `/opt/wellcum`. Установить Node.js и Caddy. Создать отдельного системного пользователя и группу `wellcum`; unit использует оба имени. Например, на Debian/Ubuntu: `sudo useradd --system --user-group --home-dir /var/lib/wellcum --shell /usr/sbin/nologin wellcum`. Приложение запускается без root.
2. Создать `/etc/wellcum`: `sudo install -d -m 700 /etc/wellcum`. Скопировать `deploy/wellcum.env.example` в `/etc/wellcum/relay.env`. Вписать случайный ключ из 64 hex-символов и закрыть файл правами `600`. Ключ не нужно передавать отдельным сообщением: игра включит доступ в строку приглашения. Сам файл с ключом не публиковать.
3. Скопировать `deploy/wellcum.service` в `/etc/systemd/system/`. Если `node` установлен не в `/usr/bin/node`, исправить `ExecStart`. `systemctl daemon-reload` и `systemctl enable --now wellcum`. Каталог базы `/var/lib/wellcum` создаёт systemd.
4. Направить домен на сервер. Добавить блок из `deploy/Caddyfile.example` в `/etc/caddy/Caddyfile`, заменив `game.example.com` своим доменом и сохранив уже настроенные сайты. Проверить `sudo caddy validate --config /etc/caddy/Caddyfile`, затем применить `sudo systemctl reload caddy` (при первом запуске — `sudo systemctl enable --now caddy`). Открыть порты HTTP/HTTPS; порт 8787 оставить доступным только локально. Caddy поддерживает WebSocket в `reverse_proxy` и автоматическое получение сертификата при корректном DNS и доступных портах. [Документация reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy), [HTTPS](https://caddyserver.com/docs/automatic-https).
5. Проверить `curl --fail https://ваш-домен/health`: ответ должен содержать текущую версию протокола. Затем проверить настоящий WebSocket через два игровых клиента: health не проверяет подключение и авторизацию игрока.
6. В игре: «Онлайн-комната» → «Свой сервер» → `wss://ваш-домен/rooms` и заданный ключ → создать комнату. Отправить другу полученную строку `WCB1:…`. Друг вставляет её в поле подключения. У обоих должна быть одинаковая версия игры.

Проверка и применение конфигурации описаны в [CLI Caddy](https://caddyserver.com/docs/command-line#caddy-validate) и [инструкции службы Linux](https://caddyserver.com/docs/running#linux-service).

Без TLS допускаются только локальные адреса. Для обычного публичного сервера требуется `wss://`. Ключ доступа проверяется до игровых запросов; личный токен ведущего в приглашение не входит. Сервер ограничивает размер сообщения, частоту запросов и число комнат. Смена ключа лишает старые приглашения доступа.

## Проверено и что ещё проверить

На Mac проверены самостоятельный пакет, реальный WebSocket и настольный preload с независимым гостевым процессом. Пример systemd/Caddy подготовлен для установки, но на отдельном VPS пока не развёрнут. На текущем подключении временный Cloudflare-туннель получает адрес, однако TLS-соединение с его узлом обрывается; рабочее приглашение в этом случае не выдаётся. Это не проверка связи между двумя физическими сетями.
